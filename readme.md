# 1. Введение

В рамках третьего этапа анализа программной системы проводится сравнение текущей архитектуры (**As-Is**) с предлагаемой архитектурой (**To-Be**).

Анализ выполняется на основе ранее построенных диаграмм:

- диаграммы компонентов
- диаграммы классов
- диаграммы развёртывания

Рассматриваемая система представляет собой **Telegram-бота для управления очередями студентов на учебные предметы**.

Основные технологии системы:

- Java
- PostgreSQL
- Hibernate
- Docker
- Telegram Bot API

---

# 2. Архитектура As-Is (текущее состояние)

## Общая характеристика

Текущая архитектура системы является **монолитной** и состоит из нескольких пакетов:

```
by.frozzel
 ├── bot
 ├── service
 ├── model
 └── config
```

### Основные компоненты

| Компонент | Назначение |
|-----------|------------|
| QueueBot | обработка Telegram сообщений |
| QueueService | бизнес-логика очередей |
| Model classes | сущности предметной области |
| HibernateUtil | конфигурация работы с БД |

### Структура взаимодействия

```
Telegram
   ↓
QueueBot
   ↓
QueueService
   ↓
Hibernate / PostgreSQL
```

### Основные особенности архитектуры

- бот напрямую вызывает сервисы
- сервисы работают с моделями и БД
- отсутствует явный слой репозиториев
- часть логики сосредоточена в сервисах

### Преимущества

✔ Простота реализации  
✔ Быстрая разработка  
✔ Небольшое количество компонентов  

### Недостатки

❌ Сильная связанность компонентов  
❌ Ограниченная масштабируемость  
❌ Сложность тестирования  
❌ Смешивание бизнес-логики и инфраструктурного кода  

---

# 3. Архитектура To-Be (предлагаемая)

Предлагается перейти к **многослойной архитектуре (Layered Architecture)**.

## Предлагаемые слои

```
Presentation Layer
Application Layer
Domain Layer
Persistence Layer
Infrastructure Layer
```

### Архитектурная схема

```
Telegram
   ↓
Bot Controller
   ↓
Application Services
   ↓
Domain Models
   ↓
Repositories
   ↓
Database
```

### Основные изменения

| Новый компонент | Назначение |
|----------------|------------|
| BotController | обработка сообщений Telegram |
| Application Services | координация бизнес-логики |
| Domain Models | сущности предметной области |
| Repository Layer | доступ к данным |
| Infrastructure | конфигурация и внешние сервисы |

---

# 4. Сравнение архитектур

| Характеристика | As-Is | To-Be |
|----------------|------|------|
| Архитектурный стиль | Монолит | Многослойная архитектура |
| Разделение ответственности | Частичное | Чёткое |
| Масштабируемость | Ограниченная | Более высокая |
| Тестируемость | Сложная | Упрощённая |
| Связанность компонентов | Высокая | Сниженная |
| Расширяемость | Ограниченная | Более гибкая |

# 5. Причины различий

Основные причины появления различий между архитектурами:

## 1. Рост функциональности системы

По мере развития проекта увеличивается количество:

- сущностей
- сервисов
- бизнес-операций

Монолитная структура начинает усложняться.

---

## 2. Повышение требований к поддерживаемости

Система должна:

- легче изменяться
- легче тестироваться
- проще расширяться

---

## 3. Улучшение архитектурного качества

Использование архитектурных принципов:

- **Single Responsibility Principle**
- **Separation of Concerns**
- **Dependency Inversion**

---

# 6. Пути улучшения архитектуры

## 6.1 Введение слоя репозиториев

Создать отдельный слой доступа к данным:

```
repository
 ├── StudentRepository
 ├── QueueRepository
 ├── SwapRepository
```

Это позволит:

- изолировать работу с БД
- упростить тестирование

---

## 6.2 Разделение логики бота и бизнес-логики

Текущий бот должен выполнять только:

- обработку сообщений
- маршрутизацию команд

Бизнес-логика должна находиться в сервисах.

---

## 6.3 Использование принципов SOLID

### Single Responsibility Principle

Каждый класс должен выполнять одну конкретную задачу.

### Dependency Inversion

Зависимость должна происходить от интерфейсов, а не от конкретных реализаций.

---

## 6.4 Использование архитектурных шаблонов

Рекомендуемые шаблоны:

### Repository Pattern

Позволяет отделить:

```
бизнес-логику
↓
доступ к данным
```

---

### Service Layer Pattern

Отдельный слой сервисов управляет бизнес-операциями системы.

---

### DTO Pattern

Используется для передачи данных между слоями приложения.

---

## 6.5 Улучшение структуры пакетов

Рекомендуемая структура проекта:

```
by.frozzel

controller
service
repository
model
config
dto
```

---

## 6.6 Улучшение обработки состояний бота

Использовать **State Pattern** для управления состояниями:

```
BotState
 ├── IdleState
 ├── WaitingForSubjectState
 └── SwapState
```

---

## 6.7 Улучшение логирования и обработки ошибок

Добавить:

- централизованное логирование
- обработку исключений
- мониторинг работы системы

---

# 7. Вывод

В результате анализа архитектуры системы были выявлены основные особенности текущей реализации и предложены пути её улучшения.

Текущая архитектура является простой и удобной для небольшого проекта, однако при дальнейшем развитии системы могут возникнуть проблемы:

- рост сложности системы
- высокая связанность компонентов
- сложность тестирования

Предлагаемая архитектура **To-Be** основана на многослойном подходе и использовании архитектурных шаблонов. Это позволит:

- улучшить поддерживаемость системы
- повысить масштабируемость
- упростить развитие проекта
- повысить качество программного кода.

Таким образом, проведение архитектурного рефакторинга позволит обеспечить более устойчивое и масштабируемое развитие системы в будущем.
